Repo: `C:\works\dash\tenant_dash` (Refine v5 + Vite + React 19 + TS strict, shadcn/ui).

## Goal

Add a **Users** resource to the dashboard matching the Postman `Users` folder: list, view,
edit name, delete, assign/remove role, and grant/revoke permissions. Follow the existing
Products/Categories patterns exactly.

## Verified API contract (from backend, authoritative)

Base `{{base_url}}` = `/api/v1`; all tenant routes send `x-tenant-slug` + `Bearer {{access_token}}`.

| UI action | Postman request | Backend route | Body | Notes |
|---|---|---|---|---|
| List | List Users | `GET /users` | — | Returns a plain array; each user has `role` (no `permissions`). `password`/`jti` stripped by global `ClassSerializerInterceptor`. |
| Self profile | Get My Profile | `GET /users/profile` | — | Returns `{ id, name, email, role: { id, key } \| null, permissions: string[] }` (effective keys). |
| Show | Get User By Id | `GET /users/profile/:id` | — | Returns user with `role.permissions` **and** direct `permissions`. |
| Update | Update User | `PATCH /users/:id` | `{ name?: string }` (2–100 chars) | |
| Delete | Delete User | `DELETE /users/:id` | — | |
| Assign role | Assign Role To User | `PATCH /users/:id/role` | `{ roleId: number }` | |
| Remove role | Deassign Role From User | `DELETE /users/:id/role` | — | Sets `roleId = null`. |
| Grant perms | Grant Permissions To User | `POST /users/:id/permissions` | `{ permissionIds: number[] }` | Array must be **non-empty** (400 otherwise). |
| Revoke perms | Revoke Permissions From User | `DELETE /users/:id/permissions` | `{ permissionIds?: number[] }` | Empty/omitted = revoke **all** direct permissions. |
| Role options | List Roles | `GET /roles` | — | `Role[]`, plain array; includes custom + system roles. |
| Permission options | List Permissions | `GET /permissions` | — | `Permission[]`, plain array. |

`users.controller.ts` has **no `POST /users`** and no create route. `CreateUserDto` is only used by
the public `POST /auth/register` (forces `CUSTOMER`). **Create is intentionally out of scope.**

### Guard rules enforced by the backend (`users.service.ts`)

Mirror these in the UI as UX-only guards (backend is the security boundary):

- Ranks: `SUPER_ADMIN=5, STORE_OWNER=4, ADMIN=3, CUSTOMER=0`; unknown/custom role key = `0`.
- Manage access (role change + grant/revoke) on a target only if:
  `actor === SUPER_ADMIN ? targetRank <= actorRank : targetRank < actorRank`.
- Assignable roles use the same rule against the **role being assigned** (custom roles rank 0).
- Grant ownership: `SUPER_ADMIN`/`STORE_OWNER` may grant anything; otherwise the actor must
  already own each granted key (use the actor's effective keys from `GET /users/profile`).
- `403` is returned when a guard fails; surface the backend message, do not rely on the UI guard.

## Key decisions

1. **No Create UI** — confirmed with user. Users resource declares `list`/`show`/`edit` only, so
   `ListViewHeader` hides the create button automatically (it checks `resource.create`).
2. **Detail endpoint override** — the generic `getOne` builds `${resource}/${id}` = `users/:id`
   (404). Extend `dataProvider.getOne` to honor `meta.detailPath` as the base path, resolved by a
   small exported helper so it is unit-testable. Users pages pass
   `meta: { detailPath: "users/profile" }`. Products/Categories are unaffected.
3. **Access management lives on the Edit page** (name form + Role card + Permissions matrix);
   the Show page is read-only. Edit uses `redirect: false` so saving the name keeps the admin on
   the page.
4. **Mutations go through Refine** (`useCustomMutation`) and **reads through Refine hooks**
   (`useList`, `useCustom`), so notifications and cache invalidation stay consistent with the app.
5. **Direct vs inherited permissions** — only direct grants are toggleable; role-inherited
   permissions render checked + disabled with a "From role" hint.

## Failure modes / edge cases

- Actor lacks `users:read`/`users:update` → backend `403`; render the error, keep the list usable.
- `POST /users/:id/permissions` with an empty array → `400`; UI never sends empty (toggles only).
- Target role or actor rank equal/higher → guards disable controls and backend returns `403`.
- Self delete: backend permits it; disable the row action for the current identity.
- `GET /users` ignores pagination params → client-side pagination/sorting via the existing provider
  fallback (`applyPagination`/`applySorters`); ensure initial sorter is `createdAt desc`.
- Detail `meta.detailPath` must be passed to **every** users `getOne` path (`show` + `edit`), or the
  request falls back to `users/:id` and 404s.
