# Multi-tenant k6 load tests

Load tests for the `saas_store_api` that exercise it as a real multi-tenant SaaS
system: at least 10 tenants, several users per tenant, deterministic tenant
assignment per virtual user, validation before load, and per-tenant reporting.

The tests never fall back to a single `demo` tenant. If fewer than 10 tenants are
configured, or the prepared dataset is missing, the run fails fast.

## Layout

```
load-tests/k6/
  .env.example        # configuration reference (copy to .env, do not commit)
  config.js           # env parsing, fail-fast tenant validation, distribution
  main.js             # all scenarios: browse, cart, checkout, isolation
  isolation.js        # standalone tenant-isolation scenario
  validate.js         # pre-run validation of every tenant and user
  lib/
    dataset.js        # loads the seeded dataset, assigns tenants/users to VUs
    api.js            # tenant-aware HTTP helpers, per-VU token cache
    metrics.js        # per-tenant metrics and summary rendering
    flows.js          # scenario implementations
  data/dataset.json   # generated by the seed script (gitignored)
  results/            # generated summaries (gitignored)
```

The seed script lives with the other manual integration scripts:

```
apps/api/test/seed-load-test.ts
```

## Prerequisites

1. PostgreSQL running and `apps/api/.env` configured:
   ```bash
   docker compose up -d postgres
   ```
2. Raise the global rate limit for the load window. The API registers a global
   `ThrottlerGuard`, so a load test from a single IP will otherwise receive
   `429`s. In `apps/api/.env`:
   ```env
   THROTTLE_LIMIT=1000000
   THROTTLE_TTL=1
   ```
   Restore the normal values after the run.
3. Start the API:
   ```bash
   pnpm --filter saas_store_api dev
   ```
4. Install k6 (`https://grafana.com/docs/k6/latest/set-up/install-k6/`).

## Configure

Copy the template and edit it:

```powershell
Copy-Item load-tests\k6\.env.example load-tests\k6\.env
```

`K6_TENANTS` must list at least 10 slugs:

```env
K6_TENANTS=tenant-1,tenant-2,tenant-3,tenant-4,tenant-5,tenant-6,tenant-7,tenant-8,tenant-9,tenant-10
```

k6 does not read `.env` files, so export the values into the shell before each
command. PowerShell:

```powershell
Get-Content load-tests\k6\.env |
  Where-Object { $_ -match '^\s*[^#].*=' } |
  ForEach-Object {
    $name, $value = $_ -split '=', 2
    Set-Item "env:$($name.Trim())" $value.Trim()
  }
```

bash:

```bash
set -a; source load-tests/k6/.env; set +a
```

## Seed test data

The seed script provisions tenants, roles, an owner and N customers per tenant,
N products per tenant, and a default address per user. It is idempotent and
consumes the prepared data directly through the Nest application services, so it
is not subject to HTTP rate limits.

Run from the repository root (after exporting the env above):

```bash
pnpm --filter saas_store_api seed:load
```

or directly from `apps/api`:

```bash
npx ts-node -r tsconfig-paths/register test/seed-load-test.ts
```

It writes `load-tests/k6/data/dataset.json` (gitignored). Use `K6_USERS_PER_TENANT`
and `K6_PRODUCTS_PER_TENANT` to size it; the defaults are 20 and 10. Prefer more
users than virtual users. No real credential is committed: `K6_PASSWORD` comes
from the environment and only the generated dataset stores it.

## Validate before load

Every configured tenant must exist, resolve, authenticate all its users, expose
products, and reject a token issued for another tenant:

```bash
k6 run validate.js
```

Run from `load-tests/k6`. The script exits non-zero on the first failing tenant.
It checks:

1. At least 10 tenants are configured (enforced at init).
2. Each tenant resolves via `GET /store/info` and returns its own slug.
3. Each tenant returns products.
4. Every seeded user authenticates and can call a tenant-scoped endpoint.
5. A token from tenant A is rejected (403) under tenant B's context.

## Run the load test

```bash
k6 run main.js          # all scenarios
k6 run isolation.js     # tenant-isolation scenario only
```

`main.js` runs four scenarios concurrently:

| Scenario | Purpose |
| --- | --- |
| `browse` | Public `GET /store/info`, `/products`, `/products/:id` per tenant |
| `cart_flow` | Authenticated add/update/remove cart item |
| `checkout_flow` | Authenticated add to cart and `POST /orders` |
| `tenant_isolation` | Non-destructive cross-tenant token rejection |

Sizing uses `K6_LOAD_VUS` (default 1000) and `K6_LOAD_DURATION` (default `2m`).
The cart and checkout scenarios use a fraction of `K6_LOAD_VUS`, so the total
virtual-user count is higher than `K6_LOAD_VUS`. Do **not** use `K6_VUS` /
`K6_DURATION`: those names are reserved by k6 and make it replace the script
scenarios with a `default` executor, which fails with `function 'default' not
found in exports` because `main.js` has no default export.

## Tenant and user distribution

Tenant and user are assigned deterministically from the virtual user id, not
randomly per request:

- `tenant = slots[(VU - 1) % slots.length]`
- `user index = floor((VU - 1) / slots.length) % usersPerTenant`

With even distribution, VU 1..10 map to tenant-1..tenant-10 and repeat, so the
first ten virtual users always cover every configured tenant and every tenant
receives traffic. Each VU keeps its tenant for the whole run and caches its
token, so auth is exercised once per VU.

Set `K6_TENANT_WEIGHTS` to one integer per tenant for an uneven distribution.
Every tenant keeps a weight of at least 1, so no tenant is starved.

## Reporting

`handleSummary` prints an overall summary and a per-tenant breakdown, and writes
`results/summary.json` and `results/summary.txt`:

```
Overall:
  p50, p95, p99, error rate, RPS

Per tenant (requests, errors, isolation failures, p95, p99, RPS)
```

Per-tenant data comes from the `tenant` metric tag, so a hot or slow tenant
cannot hide behind the global aggregate.

## Thresholds

- `http_req_failed` rate `< 1%`
- `http_req_duration` p95 `< 1000ms`, p99 `< 2500ms`
- `tenant_isolation_failures` count `== 0`

The isolation scenario marks the intentional cross-tenant `403` as an expected
response, so it does not count as a failure.
